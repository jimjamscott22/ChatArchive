CA-SEC-01 · CWE-306

Network-exposed archive API lacks authentication

High

The supplied development and packaged entry paths listen on 0.0.0.0:8000, while archive routes perform reads and destructive mutations without authenticating the caller or scoping records to an owner. A client that can reach the listener can act with the application’s database authority.

Attacker Mallory, an unauthenticated client with network reachability to the backend.
Protected asset Alice’s conversation content, archive organization, import history, and settings.
Violated invariant Private archive operations must require an authorized principal.

Source-established attack path

  1. The repository launchers execute app.main, and both runtime branches bind Uvicorn to all interfaces.
  2. GET /conversations queries the unscoped conversation table and returns record IDs and metadata.
  3. GET /conversations/{id} retrieves the selected conversation and serializes complete message content without a credential or owner check.
  4. DELETE /conversations/{id} deletes the selected record and commits. Bulk conversation deletion and import-history deletion expose broader destructive variants.
@app.get("/conversations/{conversation_id:int}", response_model=ConversationDetail)
def get_conversation(conversation_id: int, db: Session = Depends(get_db)):
    conversation = db.query(Conversation).filter(
        Conversation.id == conversation_id
    ).first()
    ...
    return conversation

@app.delete("/conversations/{conversation_id:int}")
def delete_conversation(conversation_id: int, db: Session = Depends(get_db)):
    ...
    db.delete(conversation)
    db.commit()

Evidence

  • backend/app/main.py:63–71 — application setup includes CORS, but no global authentication dependency.
  • backend/app/main.py:81–125 and 282–320 — unscoped collection, detail, and delete paths.
  • backend/app/schemas.py:89–138 — conversation detail responses include message content.
  • backend/app/main.py:507–560 and 1320–1358 — bulk and import-history deletion paths.
  • backend/app/main.py:1363–1918 — unauthenticated settings, tag, project, association, and auto-tag operations.
  • backend/app/database.py:83–93 — get_db supplies an unrestricted application session; it is lifecycle management, not authentication.
  • backend/app/main.py:2067–2075, scripts/dev.sh:33–35, scripts/dev.ps1:22–23 — supplied launch paths bind to 0.0.0.0:8000.

Constraints and counterevidence

  • Exploitation requires actual network reachability. The source does not prove exposure to the public Internet or that a firewall permits the connection.
  • CORS limits response sharing to http://localhost:5173 and constrains some cross-origin browser requests. It does not authenticate direct HTTP clients or other LAN hosts.
  • Supabase settings responses omit the service-role key. Storage download and delete helpers exist, but the reviewed API does not expose routes for them.
  • The two synchronization routes are placeholders and do not perform full synchronization.

Recommended remediation

  1. Bind to 127.0.0.1 by default. Make LAN listening an explicit, security-sensitive opt-in.
  2. Require authentication as an application-level or protected-router dependency on every non-health route. For the current single-owner design, a generated high-entropy API token is a reasonable minimum boundary.
  3. If multiple users are supported, add durable owner identity and enforce it in every query, mutation, import-history record, project/tag association, and storage object path.
  4. Keep privileged database and Supabase credentials server-side. Treat CORS as browser policy, not access control.
  5. Add route tests for missing, invalid, expired, and valid credentials, plus cross-owner access tests if multi-user support is introduced.
CA-SEC-03 · CWE-73 (best fit)

Import filenames can overwrite same-day raw export objects

Medium

Each import endpoint uploads raw bytes to optional Supabase storage before JSON decoding and source-specific validation. The object key combines a fixed provider, the current UTC date, and the client-supplied filename; upload explicitly enables upsert. Reusing all three key components can replace an existing raw export even if parsing later rejects the request.

Attacker Mallory, a reachable unauthenticated client who controls the multipart filename and bytes.
Protected asset Alice’s current-day raw export object in the configured Supabase bucket.
Violated invariant An unvalidated import must not replace an existing archive object by filename collision.

Source-established attack path

  1. A source-specific import handler accepts UploadFile.filename after checking only that it ends in .json.
  2. When Supabase is configured, the handler calls upload_export_file before json.loads and before the source parser.
  3. The helper constructs <source>/<UTC-date>/<filename> and uploads with upsert: true.
  4. A request using Alice’s provider, same-day filename, and a body no larger than 50 MiB targets the same key. If storage accepts the upload, later parser rejection does not restore the prior object.
timestamp = datetime.utcnow().strftime("%Y-%m-%d")
storage_path = f"{source_type}/{timestamp}/{filename}"

client.storage.from_(SUPABASE_BUCKET_NAME).upload(
    path=storage_path,
    file=content,
    file_options={"content-type": "application/json", "upsert": "true"},
)

Evidence

  • backend/app/main.py:796–847, 948–998, 1053–1103, and 1158–1208 — all four handlers upload before decoding and parsing.
  • backend/app/storage.py:35–87 — conditional storage, 50 MiB cap, deterministic key, and overwrite-enabled upload.
  • backend/app/main.py:1954–1981 and backend/app/storage.py:90–128 — unauthenticated listing forwards the caller’s source_type as a storage path and may make an exact collision easier.
  • backend/app/supabase_client.py:12–33 — storage is conditional on a Supabase URL and service-role key.

Constraints and counterevidence

  • The primitive is limited to the same provider prefix, UTC date, and filename. It does not establish an arbitrary filesystem write or overwrite of unrelated storage prefixes.
  • The application-managed storage helper skips bodies larger than 50 MiB.
  • Supabase must be configured, the bucket must exist, and the upload must succeed. Missing or rejecting storage prevents the overwrite.
  • The source establishes raw-object integrity loss only—not modification of already imported database records, code execution, or disclosure of the service-role credential.
  • The listing route’s exact runtime metadata was not observed, and upload errors are not a reliable overwrite oracle because helper failures are swallowed.

Recommended remediation

  1. Decode and fully validate an import before attempting to persist its raw bytes.
  2. Generate an immutable server-side object identifier, preserve the client filename only as metadata, and disable upsert for raw exports.
  3. If logical replacement is required, make it an authenticated, owner-scoped, explicit compare-and-replace operation.
  4. Authenticate and authorize import and storage-listing routes; validate listing sources against the supported provider set.
  5. Propagate storage failures and define transaction/cleanup behavior between raw storage and database import.
CA-SEC-04 · CWE-770

Import endpoints lack aggregate resource controls

Medium

The four unauthenticated import routes cap each request at 100 MiB, but they have no rate, concurrency, aggregate in-flight byte, database-growth, or object-storage quota. Repeated valid requests persist conversations and messages; overlapping requests can retain independent raw and parsed representations; configured Supabase storage can receive additional objects under distinct filenames.

Attacker Mallory, a reachable unauthenticated client sending repeated or overlapping imports.
Protected asset Backend availability and bounded database/object-storage consumption.
Violated invariant Untrusted clients must not consume unbounded aggregate work or persistent capacity.

Source-established resource path

  1. Each handler reads up to MAX_IMPORT_BYTES + 1 and retains the accepted body in memory.
  2. The request may be copied to storage, decoded into a JSON object graph, normalized into provider-specific records, and reserialized as per-conversation raw JSON.
  3. Successful imports create conversation and message rows; a pre-parse import-history commit means malformed accepted-size requests still leave a small failure record.
  4. No source-level authentication, rate limit, import semaphore, queue, aggregate byte budget, or persistence quota bounds repeated admitted work.
MAX_IMPORT_BYTES = 100 * 1024 * 1024

raw = await file.read(MAX_IMPORT_BYTES + 1)
if len(raw) > MAX_IMPORT_BYTES:
    raise HTTPException(status_code=413, detail="File too large (max 100 MB)")

# No cross-request admission or aggregate budget surrounds this work.

Evidence

  • backend/app/main.py:61, 805–807, 958–960, 1063–1065, and 1168–1170 — exact 100 MiB per-request checks.
  • backend/app/main.py:809–892, 962–1040, 1067–1145, and 1172–1250 — storage, parse, normalization, ORM persistence, and response work.
  • backend/app/importers/chatgpt.py:133–181 and the other provider parsers — normalized lists and per-conversation serialization are accumulated during parsing.
  • backend/app/storage.py:35–71 — optional storage adds a second sink, with a 50 MiB per-object cap but no aggregate quota in this helper.
  • backend/app/database.py:49–58 — connection-pool bounds constrain database connections, but do not bound request buffering or parser admission.

Constraints and counterevidence

  • The application rejects a single request larger than 100 MiB, and the storage helper skips a single object larger than 50 MiB. This is not an unbounded single-read finding.
  • Reusing the same provider/date/filename targets the same upsert key; distinct filenames are needed for expected storage object-count growth.
  • Disabling Supabase storage removes the object-storage branch, but not parsing, database work, or import-history growth.
  • Optional duplicate merging can suppress some repeated source IDs, but distinct IDs remain new and storage upload occurs first.
  • No outage threshold, memory multiplier, concurrency count, monetary cost, or observed production impact is claimed. Runtime behavior depends on deployment limits and infrastructure not represented in the repository.

Recommended remediation

  1. Authenticate imports and add per-principal plus source-address rate limits.
  2. Reserve an aggregate in-flight byte budget before reading uploads and place a global bounded queue or semaphore ahead of expensive work.
  3. Stream or spool uploads to bounded temporary storage, parse and persist in bounded batches, and clean up on failure or cancellation.
  4. Make imports idempotent with provider-appropriate uniqueness rules, and add owner-scoped database and storage quotas plus retention policies.
  5. Configure transport-level body limits, deadlines, observability, and provider-side hard limits as defense in depth.

Recommended remediation order

  1. Establish the access boundary. Default to loopback and require authentication for every non-health route. This reduces reachability for all three findings.
  2. Make raw exports immutable by default. Validate first, generate server-side object IDs, disable implicit upsert, and scope storage operations to an authenticated owner.
  3. Bound import work across requests. Add rate and concurrency admission, aggregate byte reservations, quotas, idempotency, and cleanup behavior.
